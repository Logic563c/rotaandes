# Decisiones técnicas de RotaAndes

## Autenticación y perfil (fase autorizada)

- **Alcance:** registro, login, `/auth/yo`, perfil y middleware reutilizable de autenticación/roles. No cambia el esquema, la migración ni el contrato original. No se crean cuentas técnicas, pantallas agrícolas ni rutas demostrativas en producción.
- **Dependencias:** bcrypt 6.0.0, jsonwebtoken 9.0.3, Zod 4.6.7, express-rate-limit 8.7.3 y React Router DOM 7.18.5, con requisitos compatibles con Node 24.20.0. Se conserva Prisma 7.10.1. bcrypt dispone de binarios precompilados; su script se autoriza únicamente para esa versión en `allowScripts`.
- **Contraseñas:** mínimo 15 caracteres Unicode al registrar, máximo 72 bytes UTF-8 y sin NUL, sin recorte ni normalización de claves. Hash bcrypt asíncrono con coste 12 y sal por contraseña. Login admite claves anteriores dentro del límite de bytes. Ante correo inexistente se compara con un hash efímero para reducir diferencias de tiempo; no es una cuenta ni una contraseña predeterminada. [Documentación de bcrypt](https://github.com/kelektiv/node.bcrypt.js#security-issues-and-concerns).
- **Entradas:** esquemas Zod estrictos rechazan campos adicionales. Correo normalizado por trim/minúsculas, sin cambiar puntos o `+`. Nombre 2–120, parroquia hasta 100, teléfono opcional hasta 25 caracteres con 7–15 dígitos, prioridades enteras 1–5. Parroquia/teléfono vacíos se guardan como NULL; un perfil sin campos se rechaza. JSON hasta 16 KB; errores en español con `{ error }`. Duplicados responden 400 dentro del contrato. La limitación añade 429 y Retry-After para expresar el exceso de solicitudes; no cambia ningún endpoint ni cuerpo de éxito.
- **JWT:** HS256 exclusivo, 15 minutos, `sub` UUID, emisor `rotaandes-api`, audiencia `rotaandes-web`, firma/expiración verificadas. El rol procede de PostgreSQL en cada solicitud, nunca de claims o campos del cliente. Las consultas públicas seleccionan campos sin hash y la serialización mantiene snake_case. [Opciones de verificación](https://github.com/auth0/node-jsonwebtoken#jwtverifytoken-secretorpublickey-options-callback).
- **Secreto:** `auth:preparar` reutiliza un secreto existente válido o añade 48 bytes criptográficamente aleatorios codificados base64url al `.env` privado. Nunca lo muestra. El arranque rechaza secretos ausentes, formato inválido o menos de 64 caracteres; el ejemplo permanece vacío. No se modifican las credenciales PostgreSQL.
- **Sesión frontend:** Bearer en `sessionStorage` por pestaña y duración corta; no localStorage ni cookies. TanStack Query administra usuario/caché y React Context solo token/acciones de sesión, sin otro gestor global. `/yo` debe confirmar la sesión antes de mostrar vistas privadas; los fallos bloquean la vista, permiten reintentar y un 401 elimina la sesión. Logout limpia token y caché, pero el JWT sin revocación permanece válido hasta expirar. La lectura de `exp` en el navegador solo anticipa el cierre; el servidor es la autoridad.
- **Límites locales:** sessionStorage es vulnerable al robo por XSS y puede restaurarse con una sesión del navegador; no garantiza revocación. No hay refresh tokens, revocación, recuperación de claves ni verificación de correo. Antes de despliegue se revisarán HTTPS, encabezados CSP y proxy. El limitador en memoria aplica 5 registros y 10 logins por IP/15 minutos, reinicia con el proceso y no se comparte entre réplicas. Se conserva `trust proxy=false`; CORS local exacto permite GET/POST/PUT y Authorization/Content-Type. [Configuración del limitador](https://express-rate-limit.mintlify.app/reference/configuration).
- **Pruebas sin datos residuales:** HTTP/Prisma con transacciones revertidas en la base aislada; E2E arranca backend con `NODE_ENV=test`, valida exclusivamente `TEST_DATABASE_URL` y un secreto efímero. Las cuentas E2E usan correos y claves aleatorios, se eliminan por correo exacto en `finally` y se comprueba el estado posterior. No hay escritura de pruebas en desarrollo ni cambios de migraciones. Se deshabilitan trazas de navegador para no registrar credenciales/Bearer; capturas y artefactos se ignoran.
- **Roles futuros:** `permitirRoles` distingue agricultor/técnico y se prueba contra la base. El filtrado por propietario se incorporará en las rutas de recursos cuando se autorice el CRUD; este middleware no concede permisos de edición sobre recursos ajenos.

## Base de la aplicación

- **Entorno:** Node 24.20.0 y npm 11. Se usan workspaces de npm con un único archivo de bloqueo para reproducir la instalación y comandos en la raíz o en cada paquete.
- **Scripts de instalación:** npm 11.19 registra en `package.json` la autorización del script de instalación de `esbuild@0.28.2`, necesario para sus binarios de desarrollo. La autorización se limita a esa versión y no habilita scripts de todos los paquetes.
- **Herramientas:** Vite 8, React 19, TailwindCSS 4 con `@tailwindcss/vite`, Express 5 y TypeScript 5.9 en modo estricto. Vitest ejecuta las pruebas; Supertest verifica HTTP del backend y Testing Library con jsdom verifica la interfaz. Los rangos se resuelven en `package-lock.json`; se consultaron los requisitos de Node de Vite y Vitest antes de instalar.
- **Base HTTP:** se conserva `GET /api/health` con `{ "ok": true }` y la página inicial que lo consulta mediante `frontend/src/lib/api.ts` y TanStack Query. El estado se valida en ejecución y la solicitud tiene un límite de ocho segundos. No se crean rutas, tipos ni mocks de módulos futuros.
- **Desarrollo local:** backend en 3000, ligado a `127.0.0.1`; frontend en `localhost:5173` con puerto estricto. CORS admite únicamente el origen local configurado. Los cambios para hosting se definirán en otra tarea.
- **Entorno:** la etapa de persistencia añadió `DATABASE_URL` y `TEST_DATABASE_URL` solo al backend; la fase autorizada de autenticación añade `JWT_SECRET`. Sus ejemplos son ficticios o vacíos y los valores reales se guardan en `.env` excluido de Git.
- **Contrato y datos:** la persistencia implementa el modelo de la sección 5 sin modificar `PROYECTO.md`, `AGENTS.md` ni el contrato HTTP. La fase actual incorpora exclusivamente autenticación y perfil; CRUD, semillas, datos agrícolas e integraciones externas quedan pendientes.
- **Navegador real:** Playwright comprueba los artefactos compilados en escritorio y celular, contra el backend real. Usa Edge instalado en Windows o Chromium en otros sistemas, sin descargar un navegador durante la instalación de paquetes.
- **Lint:** ESLint 10 y typescript-eslint 8. Se aplican overrides limitados a `minimatch` de ESLint, `@eslint/config-array` y `@typescript-eslint/typescript-estree` para usar la versión corregida 11, debido al [aviso GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249). Se verifica la compatibilidad con lint, tipos y pruebas; revisar estos overrides cuando las herramientas incorporen la corrección directamente.

Referencias oficiales consultadas: [Vite](https://vite.dev/guide/), [TailwindCSS con Vite](https://tailwindcss.com/docs/installation/using-vite), [Express](https://expressjs.com/en/starter/installing/) y [Vitest](https://vitest.dev/guide/).

## Persistencia PostgreSQL + Prisma

- **Versiones y compatibilidad:** Prisma CLI, Client y `@prisma/adapter-pg` se fijan a **7.10.1**, con `pg` **8.23.1**. Se conserva Node **24.20.0**, TypeScript **5.9.3**, ESM y Express **5**. Prisma 7 exige TypeScript 5.4 o superior y admite Node 24. Se evitó el `latest` del CLI, que al auditar resolvía a Prisma 8 candidata; Express no interviene en la generación ni en el adaptador. Referencias: [versión exacta 7.10.1](https://github.com/prisma/orm/releases/tag/7.10.1), [guía v7](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7) y [configuración v7](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference).
- **Generación explícita:** se usa `provider = "prisma-client"`, salida `src/generated/prisma`, formato ESM e imports `.js` para la compilación NodeNext. La URL reside en `prisma.config.ts`; no en el esquema. El adaptador `PrismaPg` administra el grupo de conexiones. El módulo `src/lib/prisma.ts` crea una sola instancia de forma diferida y permite cerrarla. Los scripts oficiales de instalación de Prisma y sus motores se autorizan solo para la versión 7.10.1.
- **Nombres y tipos:** modelos singulares en PascalCase y campos internos en camelCase con `@map` y `@@map`. Se conservan los seis nombres físicos, UUID con `gen_random_uuid()` en PostgreSQL, identificadores textuales, tipos nativos y nulabilidad del SQL. Las prioridades y timestamps con valor predeterminado siguen siendo opcionales, porque el SQL de referencia permite NULL. No se usa `@updatedAt`, ya que el contrato solo define `DEFAULT now()`.
- **Restricciones SQL:** los roles se mantienen como TEXT con CHECK, sin introducir un enum PostgreSQL. Los cuatro CHECK se añaden al SQL de la migración porque Prisma no los representa en el modelo. El índice único de correo se adjunta como restricción UNIQUE. El DDL generado por Prisma omite NOT NULL en arreglos; se añade expresamente a `meses_siembra` y `secuencia`. Los tests consultan PostgreSQL para proteger esas diferencias. No se añaden CHECK agronómicos que no existan en el contrato.
- **Migración inicial:** `20261107000100_esquema_inicial`, preparada con `prisma migrate diff --from-empty --to-schema ... --script` y revisada antes de su aplicación. El SQL completo se ejecuta dentro de BEGIN/COMMIT. Las relaciones conservan ON UPDATE NO ACTION y los dos borrados CASCADE especificados. Se aplica con Prisma Migrate `migrate deploy`, sin `db push`, reset ni shadow database. No se concede CREATEDB ni SUPERUSER a la aplicación. Los scripts de migración y estado validan primero que exista la configuración local, evitando interpretar una salida vacía del CLI como una verificación de conexión.
- **Credenciales y permisos:** el asistente PowerShell reutiliza `.env`, variables PostgreSQL o pgpass antes de solicitar una clave. Usa entrada oculta una vez por rol, pasa la clave solo al entorno del proceso hijo psql y codifica los caracteres reservados al escribir las URLs de forma atómica. Utiliza `postgres` únicamente cuando necesita inspección administrativa o crear una base autorizada con propietario `rotaandes_app`. La tarea de VS Code abre una terminal integrada con foco; su estado público se registra en `.tmp/`, ignorado y sin secretos. No cambia roles ni otras bases. El código y las pruebas rechazan otros servidores, roles administrativos y nombres de base fuera de los destinos autorizados. La captura separada de stdout/stderr evita que PowerShell 5 transforme un fallo de autenticación esperado en una excepción antes de solicitar la clave.
- **Pruebas aisladas:** el asistente reutiliza `TEST_DATABASE_URL` o una base compatible existente propiedad de la aplicación. Solo crea una con sufijo aleatorio si no encuentra ninguna, evitando acumulaciones al reejecutarlo. `test:db` reproduce las migraciones allí y ejecuta pruebas SQL y Prisma; todas sus escrituras terminan en rollback. Las fixtures son sintéticas, temporales y sin significado agronómico. No se insertan semillas ni se borran datos previos de desarrollo. La prueba de autenticación incorrecta solo intenta una conexión rechazada; no cambia contraseñas.
- **Verificación del proceso y de persistencia:** `/api/health` mantiene su semántica HTTP independiente. `db:verify` comprueba explícitamente la conexión de Prisma sin añadir rutas. `verificarEsquema.sql` permite inspeccionar propietario, tipos, valores predeterminados, restricciones y migraciones en psql o pgAdmin mediante una transacción de solo lectura.

Los CHECK y la nulabilidad de los arreglos deben conservarse al revisar futuras migraciones. No editar migraciones ya aplicadas. Para cambios nuevos, generar un borrador revisable y aplicar solo los cambios autorizados; consultar la [edición de migraciones de Prisma v7](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/customizing-migrations).

- **Compatibilidad del asistente con PowerShell 5:** se usa el operador `-split` para dividir usuario y clave; la sobrecarga de `String.Split` con arrays e integer puede resolverse como `StringSplitOptions` y fallar en esa versión. El reemplazo atómico de `.env` usa `[NullString]::Value`, porque `$null` puede convertirse en una ruta vacía en la llamada a `File.Replace`. Las comprobaciones de `tests/scripts/configurarBaseLocal.test.ps1` cubren caracteres reservados, pgpass y creación/reemplazo de archivos sin conectar ni utilizar credenciales reales. Los archivos PowerShell incluyen BOM UTF-8 para conservar el español en Windows PowerShell 5.
- **Errores sin credenciales:** la validación de URLs del backend descarta el error nativo que podría incluir su entrada. La prueba de contraseña incorrecta compara únicamente el estado de conexión y SQLSTATE, para que el reporter nunca reciba el cliente de pg ni su configuración si el servidor permite una conexión inesperada.
- **Comparación de timestamps:** el catálogo PostgreSQL puede mostrar `timestamp(6) with time zone` al declarar explícitamente la precisión con Prisma. Las pruebas normalizan únicamente esa precisión de microsegundos a `timestamp with time zone`; no aceptan una precisión inferior ni cambian la migración aplicada.
- **Auditoría de conexión previa al commit:** se verificó con el parser de pg instalado, sin conectar, que parámetros de consulta como `host`, `port` y `user` pueden sobrescribir la autoridad de la URL. La validación local ahora solo permite un `schema=public` opcional y rechaza fragmentos y duplicados. No cambia las URLs configuradas ni el modelo de datos; impide que un destino aparentemente local termine interpretándose como otro servidor o rol. Los casos de regresión cubren desarrollo y pruebas.
